# TASK-015 v2 — 저장·기록 API 및 삭제 절차

2026-11-10 / dev. 로컬 구현·합성 검증용 설계다. 실환경 DB 적용과 Worker 배포는 하지 않았다.

## 데이터와 권한

- 기존 Auth·활성 멤버십·pilot_submissions를 재사용한다. 최초본에는 UPDATE 권한을 주지 않는다.
- pilot_revisions는 중심 생각·핵심 정보·보조 정보·관계 설명·Retell만 별도 행으로 추가한다. 구조도 유형·감상·새 어휘·관심 분야·원문 재확인 여부는 최초본에 유지한다.
- 원본 id와 owner_id의 복합 외래 키, 본인 RLS, 활성 회원 검사로 타인 원본에 본인 수정본을 연결하는 요청을 거절한다. 수정본 UPDATE·DELETE 및 소유권·원본 연결 변경 권한은 없다.
- 수정본 id·saved_at은 DB 기본값으로만 발급한다. 인증 역할은 지정된 입력 열만 INSERT할 수 있다. 최초본도 입력 열 INSERT로 한정하며 기존 SELECT·INSERT RLS는 유지한다.
- requestId는 패널이 발급하는 UUID다. (owner_id, submission_id, request_id) UNIQUE가 동시 중복을 막는다. 같은 요청의 내용이 다르면 409, 같으면 기존 버전을 반환한다. 다른 요청은 이전 수정본을 덮지 않고 각각 보존한다.
- 버전 식별자는 DB id다. 목록과 이력은 saved_at DESC, id DESC로 정렬한다. 같은 시각은 id로 결정하며, 사용자에게 연속 번호나 동시 요청의 완료 순서를 보장하지 않는다. 원본·수정본용 복합 인덱스를 둔다.
- Worker는 service_role을 쓰지 않고 사용자 JWT로 DB에 접근한다. 허용 Origin은 기존 확장 Origin 하나를 그대로 사용한다. Origin 없는 GET도 인증·활성 회원·RLS를 거친다. Origin 없는 POST와 다른 Origin은 거절한다.

## 공통 API

기존 /submissions POST 및 ?sessionId= GET은 유지한다. 새 경로는 같은 Worker의 /submissions 아래다. 인증 토큰은 Authorization 헤더에만 넣는다.

| 메서드·경로 | 내용 |
|---|---|
| GET /submissions/records?capabilities=1 | 인증·활성 회원 확인 후 limit=0으로 필요한 테이블·열·관계를 검사. recordsApiVersion=1, ready=true일 때만 답안 전송 |
| GET /submissions/records | 본인 최근 기록 10개와 nextCursor |
| GET /submissions/records/:submissionId | 최초본 전체와 서버 저장 시각 |
| GET /submissions/records/:submissionId/revisions | 수정 이력 10개와 nextCursor |
| POST /submissions/records/:submissionId/revisions | requestId와 answers의 다섯 항목 저장. Idempotency-Key는 requestId와 일치해야 함 |
| GET /submissions/records/:submissionId/revisions/:requestId | 같은 저장 요청의 별도 재조회 |

- 목록은 최초본 식별자·시각·선택 글 정보·수정본 유무만 반환한다. 답안·사용자 식별자는 목록에 포함하지 않는다. 수정본 유무는 중첩 조회 1개로 제한한다.
- cursor는 서버 저장 시각과 행 id다. 사용자 답안·인증값은 포함하지 않는다. 동일 정렬 키로 이전 페이지를 조회하며 offset 이동에 따른 중복을 피한다.
- 400 잘못된 입력·커서, 401 인증 만료/실패, 403 비활성·권한/Origin 거절, 404 본인 기록 없음/삭제/타인 기록, 409 동일 요청 내용 충돌, 503 저장 또는 확인 불가를 사용한다. 타인 기록의 존재는 알리지 않는다.
- 저장 응답 후 같은 requestId를 다시 조회하고 id·시각·다섯 항목이 일치해야 완료로 표시한다. 응답 유실·오프라인·재조회 불일치는 미확인 상태로 유지한다. 재시도는 같은 식별자·내용이며 실패 뒤 추가 편집은 다음 명시 저장에서 전송한다.
- 패널은 자동 재시도하지 않는다. 기록 요청에는 15초 timeout과 no-store를 적용한다.
- 구형 서버의 준비 검사 400/404/405는 records_api_unavailable로 구분하고 답안 POST를 보내지 않는다. 알려진 DB 테이블/열/관계 오류는 records_schema_missing으로 반환한다. 입력 형식 400을 네트워크 연결 실패로 표시하지 않으며 서버의 오류 전문은 노출하지 않는다.
- 준비 검사는 어댑터 안에서 공유·성공 캐시한다. 실패는 캐시하지 않아 서버 준비 후 같은 요청으로 다시 저장할 수 있다. 마이그레이션 커밋 시 PostgREST 스키마 캐시 갱신을 알린다.

## 글 식별 정보의 최소 범위

- 2026-11-10 사용자 후속 요청에 따라 글 연결 성공 후 같은 URL로 확인한 탭의 제목을 제출 화면에 자동 입력한다. 제어문자를 정리하고 잘못된 유니코드를 보정하며 입력란의 200 UTF-16 단위 제한 안에서 서로게이트 쌍을 보존한다. 제목은 사용자가 확인·수정·삭제할 수 있고, 기존 글 정보 저장 동의를 별도로 선택한 경우에만 최초 제출의 articleTitle로 저장한다. 제목 입력 영역은 제출 화면에서 기본으로 펼친다.
- 기사 주소는 자동 수집하지 않는다. 출처 사이트 origin은 기존처럼 직접 입력하는 선택 항목이며 빈 주소와 제목만 저장하는 것도 기존 계약에서 지원한다. 제출 때 현재 활성 탭 제목을 다시 읽지 않아 연결한 글과 다른 탭 제목이 저장되는 일을 피한다.
- sourceUrl은 https://example.com처럼 사이트 origin만 허용한다. 경로·검색어·fragment·자격정보·포트·로컬 주소는 거절한다. 제목도 민감한 정보가 없는 공개 제목인지 사용자가 확인한다.
- 기존 기록에는 NULL을 유지하고 「글 정보 없음」으로 표시한다. 과거 기사·제목·URL을 추정하거나 채우지 않는다.
- 기사 전문·발췌문·AI 피드백·기존 지식은 새로 저장하지 않는다. 선택 메타데이터도 최초본과 함께 삭제한다. 실제 전송 범위 변경은 이 설계·동의 문구를 검토하고 실환경 변경 승인 후 적용한다.

## 패널 경계

- 「내 기록」은 같은 사이드패널 안에 있다. 진행 중 훈련이 있으면 미저장 입력 손실과 종료를 확인한다. 취소 또는 원문 복원 실패 시 기록을 열거나 조회하지 않는다.
- 원문 복원 확인 → 훈련·피드백·추천 세대 초기화 → articleSession 제거 → 입력 삭제 → 기록 조회 순서다. 조회 응답은 세대와 현재 기록 화면을 다시 검사한다.
- 새 독해·다른 기록 선택·로그아웃 뒤 도착하는 과거 응답은 폐기한다. 저장본을 새 독해 입력에 채우지 않으며 기록 조회 시 AI를 호출하지 않는다.
- 토큰·작성 초안·미저장 수정은 패널 메모리에만 있다. 저장 실패·401은 입력을 유지하고 상단 재로그인을 안내한다. 최초 제출이 있는 flow는 같은 계정만 재로그인할 수 있다.
- 장기 로그인·브라우저 자동 로그인·웹·로컬 AI 서버는 기록 조회의 선행 조건이 아니다.

## 조기 삭제·종료 후 삭제

- 담당: 사용자(파일럿 운영자). 조기 삭제 요청과 파일럿 종료 후 30일 이내 삭제에 최초본·수정본·선택 글 식별 정보를 함께 포함한다.
- 참가자용 삭제 UI나 인증 역할의 DELETE 권한은 추가하지 않는다. 운영자가 비공개 경로에서 요청자와 본인 원본 id를 확인한다. 참가자 신원·삭제 요청·인증값은 공개 저장소에 기록하지 않는다.
- 실환경에서 승인된 관리 도구로 대상 원본과 owner_id를 함께 확인하고, 해당 두 조건으로 원본을 삭제한다. pilot_revisions 복합 FK의 ON DELETE CASCADE로 관련 이력이 함께 제거된다. 제목·출처는 원본 열이므로 함께 제거된다.
- 삭제 뒤 관리자 DB에서 원본·연결 수정본이 0개인지 확인하고, 본인 토큰의 API 상세·수정 이력·요청별 재조회가 404인지 확인한다. 활성 원본이 없으면 수정본 재저장도 거절되어야 한다.
- 계정 전체 삭제가 요청되면 승인된 범위의 Auth·멤버십·최초본 연쇄 삭제를 별도로 검토한다. 다른 계정이나 파일럿 전체를 추정하여 삭제하지 않는다.
- 실제 백업/PITR 보존 기간·사용자 export·복제본 현황은 아직 확인하지 않았다. 온라인 DB 삭제가 기존 백업에서 즉시 소거됨을 의미하지 않는다. 운영 전 보존 기간과 복구 접근 담당을 확인하고 동의·삭제 안내에 반영한다.
- 백업을 복구하면 삭제 자료가 재등장할 수 있다. 운영자가 비공개 삭제 이력을 보관하고 복구 후 재삭제·재조회한다. 공개 문서에 실제 삭제 대상·연락처·응답을 적지 않는다.
- 로컬 합성 검증은 원본 삭제 후 수정 이력 0개, 최초본·특정 수정본·재저장 404, 선택 메타데이터가 목록에서도 사라짐을 확인했다. 실환경 삭제·백업 검증은 남아 있다.

## 검증과 적용 순서

1. 기존 공개 SQL 초안과 실환경의 RLS·열·권한 메타데이터를 대조했다. 실제 사용자·답안은 조회하지 않았다. 2026-11-10 현재 최초본 SELECT·INSERT RLS만 있고 수정본은 없다.
2. 로컬 PGlite 0.5.16(PostgreSQL WASM)에 합성 Auth 역할·사용자, 기존 초안, 신규 초안을 적용했다. Worker가 보내는 SQL을 같은 역할/JWT sub로 실행해 RLS·제약·API 경로를 검사했다. HTTP·PostgREST 변환은 테스트 어댑터이므로 실제 PostgREST 통합으로 간주하지 않는다.
3. 마이그레이션 이름은 Supabase CLI migration new로 생성했고, 저장소의 기존 server/migrations 아래에 초안으로 보관했다. 정식 적용 전 현재 스키마 차이·충돌·DB advisors와 PostgREST 스키마 캐시/관계 해석을 다시 검증한다.
4. 승인 후 스키마 적용 → 제출 Worker 배포 → 정확한 확장 Origin·기존 기능 확인 → 두 합성 사용자·비활성 사용자·직접 DB 권한·실제 Chrome 재열기/재로그인/삭제 검증을 수행한다. 새 UI를 기존 원격 Worker만으로 검증했다고 주장하지 않는다.
5. main 병합·push는 별도 승인 후 진행한다. TASK-015 AC와 TASK-017의 설치 산출물 검증은 구분한다.
