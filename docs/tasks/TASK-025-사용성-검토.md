# [TASK-025] AI 피드백 실패·재시도 사용성 검토

검토일: 2026-11-17 (Asia/Seoul). 요청서 v1: [AI 로그 활성화·사용성 검토](TASK-025-AI-로그-활성화-사용성-검토.md).

후속 상태(v2): 사용자 우선순위별 수정 지시로 1순위 전체와 2순위의 안전한 기준 정렬·최초 제출 평가 안내를 로컬 구현했다. 아래 원인·코드 설명은 v1 검토 시점의 기록이다. 현재 결과·미검증·운영 반영 조건은 [TASK-025 결과](TASK-025-결과.md)를 따른다. 인용 ID 방식·수정본 재평가·자동 재시도는 도입하지 않았다.

## 판단

운영 로그 저장을 활성화했다. 다음 제품 변경은 **오류를 구별할 수 있게 만들기 → 중복·표시 오류 제거 → 생성 형식과 검사의 불일치 줄이기** 순으로 권장한다. 검사를 통째로 없애거나 재시도를 계속 늘리는 방식은 채택하지 않는다. 이 문서는 검토안이며 아래 제품 수정·정책 변경을 배포 승인으로 해석하지 않는다.

## 실제 운영 근거

- 운영 Worker `reading-ai-pilot` 버전 `f8d429ba-c4a8-46a5-9a29-5d1d4c2127d1` 유지. 로그 설정만 API로 변경했다.
- 사용자가 제공한 저장 로그 6항목은 요청 4건이다. 피드백 실패 2건은 invocation 로그와 console 오류가 요청 ID로 각각 연결되므로 4번 실패로 세면 안 된다.
- 15:48:25.163 / 15:50:24.677 KST에 기록된 `/feedback`은 HTTP 502, 처리 시간 5.508 / 7.628초이며 두 console 오류는 `[pilot-ai] provider`다. 50초 timeout 양상이 아니다.
- 각 기록 시각에서 wallTime을 빼면 요청 시작은 약 15:48:19.655 / 15:50:17.049다. Cloudflare 제공자 통계의 15:48:19 / 15:50:17 DeepSeek 호출(모두 HTTP 200 / completed)과 초 단위로 대응한다. 제공자 요청 ID에 의한 직접 결합은 아니지만 시간과 처리 시간은 일치한다.
- 15:47:13.030의 `/recommend-article`은 HTTP 200이다. 같은 서버의 읽기 전 추천은 성공하고 피드백 경로는 실패했다. API 키 전체 장애나 AI 서버 전체 중단보다 피드백 응답 처리 쪽을 우선 조사할 근거다.
- 15:47:53.203의 `/feedback` 401은 로그 검증을 위해 Codex가 보낸 무인증 합성 요청이다. 사용자 로그인 장애로 세지 않는다. 이 요청에 붙인 합성 query가 저장 URL에서 제거된 것도 확인했다.
- `outcome:ok`는 Worker 실행이 처리되지 않은 예외 없이 끝났다는 뜻이다. HTTP 502의 제품 실패를 성공으로 해석하지 않는다. `truncated:false`도 성공/출력 정상 여부를 뜻하지 않는다.
- `$metadata.error`도 POST 주소 또는 `[pilot-ai] provider`를 반복하며 세부 탈락 사유가 없다. 저장 기능을 켜는 것만으로 JSON·종료 사유·인용·필드 오류가 구별되지는 않는다.

대기 화면은 ‘확인 중/응답을 기다리는 중’과 실제 경과 시간만 보여 준다. 현재 연결에서 알 수 없는 공급자 내부 진행률을 만들지 않는다. 피드백 실패 후에도 직접 수정·저장은 계속 가능하게 한다. 초안의 새 영구 저장은 이번 범위에 추가하지 않는다.

## 자동 재시도와 비용

현재는 자동 AI 재전송을 하지 않는 정책을 유지한다. 먼저 중복 클릭·불필요한 수동 반복을 줄인다. 분류 로그를 확보한 후 자동 재생성을 도입하려면 다음을 별도로 합의·검증한다.

- 재시도 가능 오류를 한정하고 최대 한 번, 요청 전체의 제한 시간 안에서 수행한다. timeout·통신 단절은 공급자가 이미 처리했을 수 있으므로 무조건 재전송하지 않는다.
- 추가 모델 호출도 비용/사용량 계산에 포함한다. 인증·권한·기한 확인, 취소·로그아웃·계정 변경·단계 전환 차단을 우회하지 않는다.
- 생성 결과를 서버에 재사용 보관하는 방식은 새 저장 범위·TTL·삭제·계정 결속을 먼저 검토한다. 현재 피드백 미저장 정책을 조용히 바꾸지 않는다.

## 개인정보와 로그 운영

- 요청별 고정 분류 코드와 시간/상태를 남긴다. Error.message/stack 전체나 제공자 응답 전체를 그대로 console에 내보내지 않는다. 필요한 숫자도 허용 목록으로 제한한다.
- 수신한 실제 Cloudflare invocation 샘플에는 `cf` 네트워크 메타데이터와 요청 헤더가 있다. authorization 값은 redacted이고 request.body는 없었다. 그러므로 ‘저장 로그는 상태 코드만 있다’고 설명해서는 안 된다. 원본 export를 공개 저장소에 넣지 않는다.
- AI Worker만 100% 저장 수집, URL query 제거, traces 비활성, 외부 Logpush 비활성이다. 기본 계정 보존 기간을 따르며 장기 보관을 추가하지 않았다. 추후 배포 준비본에도 이 로그 설정을 명시해야 한다.
- 현재 관리 OAuth 연결은 저장 로그 조회 API에 403을 받는다. 사용자 제공 dashboard export로 실제 저장을 검증했다. 별도 권한 확대는 하지 않았다.

## 검증 근거와 다음 구현 순서

- 로컬 합성 재현 3건: 잘못된 JSON 예시, 인증 대기 중 클릭 두 번→fetch 두 번, 동일 계정으로 가정한 토큰 문자열 변경→정상 결과가 숨겨지고 대기 문구 잔류. 실제 사용자 자료·네트워크를 사용하지 않았다.
- 재현은 현재 코드의 위험을 입증한다. 실제 로그인 갱신/브라우저 조작에서의 발생 빈도까지 검증한 것은 아니다. 특히 로그아웃·재로그인과 같은 계정의 정상 갱신을 안전하게 구별하는 것은 후속 구현의 필수 조건이다.
- 1차 구현: 분류 로그/오류 응답 → 유효한 프롬프트 예시 → 요청 잠금/인증 세대 → 안내. 사용자 코드 배포 승인 후 합성 재현과 실사용 실패율을 비교한다.
- 2차 검토: 인용 ID 방식·안전한 순서 정규화·수정본 재평가·제한 재시도. 실제 분류 결과에 맞춰 범위를 정한다.

참고: [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)은 유효한 JSON 예시, 적정 출력 제한, 공백뿐인 출력 가능성 처리를 설명한다. 따라서 JSON 모드를 지정했다는 사실만으로 피드백 계약 준수를 보증할 수 없다. 이번 로그에는 공백 출력·출력 잘림 여부가 없으므로 실제 원인으로 확정하지 않는다.
