# [TASK-024] 블록형 구조도 구현 가능성 검토

작성: 2026-11-12 (Asia/Seoul). 상태: **제안·가능성 검토, 제품 변경안 확정이나 구현 착수 승인이 아님**.

후속 상태: 사용자 「실제 초급자 구조도 학습 과정에 반영」 지시로 v8 제품 UI에 적용했다. 현재 결과·검증·설치본은 [블록 UI 결과](TASK-024-블록UI-결과.md)를 따른다. 아래는 설계 논의 당시의 검토 기록이다.

## 결론

구현 가능하다. 현재 규모인 3개 유형·2개 역할·2–8개 문장을 유지하면, 문장 블록을 선택·배열하고 직접 이어 붙이는 편집기는 중간 정도의 프런트엔드 변경으로 접근할 수 있다. 자유로운 무한 캔버스와 임의 중첩까지 구현하는 경우는 범위와 난도가 크게 늘어난다. 이 난도는 코드 구조에 근거한 추정이며 실제 드래그 프로토타입의 측정 결과나 일정 보장이 아니다.

사용자가 말한 ‘관계를 적는다’는 두 범위가 가능하다. 구조도 전체에 한 번 이유를 쓰는 방식은 기존 저장 계약을 재사용할 수 있다. 연결마다 별도 설명을 쓰고 보관하는 방식도 가능하지만 별도의 저장 계약 변경이 필요하다. 아직 어느 방식도 확정하지 않았다.

## 현재 코드에서 확인한 기반

- `reading-support.js:createEditor`는 문장 ID·원문·역할·출처·순서를 가진 노드와 ID 간 연결을 관리한다. 현재 `place`는 역할 지정이고, 임의 재배열용 메서드는 아직 없다.
- `reading-support-contract.js`는 순서 `order`와 `from/to/relationType` 연결을 검증한다. 현재 화면의 연결 시작/도착/관계 select는 이 자료를 입력하는 UI다. 같은 자료를 블록 조작으로 만들 수 있다.
- `guided-panel.js:guidedRender`와 `sidepanel.html/css`가 화면 교체의 주 대상이다. 편집기에 `move/reorder`를 추가하고 노드 ID를 유지하면 재배열 중 연결을 보존할 수 있다.
- `support-view.js`는 저장된 노드를 `order`로 정렬한다. 기존 기록 형식으로도 바뀐 문장 순서를 재현할 기반이 있다.
- 그래프 전체 설명은 기존 선택 문자열 `relation`에 저장된다. 연결 데이터와 별개의 항목이다.

## 제안하는 첫 범위

1. 후보/원문에서 문장을 고른다. AI가 준 문장과 직접 추가한 문장의 출처는 계속 구분한다.
2. 주장/근거, 원인/결과, 문제/해결책 영역에 문장 블록을 직접 놓고 순서를 바꾼다. 좁은 패널에서는 세로로 쌓는다.
3. 블록의 연결점을 직접 선택하거나 연결 슬롯에 끼워 연결한다. 연결 방향과 관계는 화면에서 확인할 수 있게 한다.
4. 연결 이유를 적는다. 첫 범위에서 전체 선택 설명을 유지할지, 연결별 설명을 도입할지는 사용자와 정한다.
5. 배치·연결을 확인하고 자기 말로 중심 생각과 Retell을 작성한다.

단순히 옆에 놓았거나 순서만 바꿨다고 관계를 생성하지 않는다. ‘연결 슬롯에 끼워 넣기’처럼 연결 의도가 분명한 사용자 동작은 직접 연결 입력으로 구현할 수 있다. 유형·역할만 선택했을 때 자동으로 완성 구조도를 채우는 동작과 구별한다.

## 범위별 서버 영향과 상대 난도

| 범위 | 예상 난도 | 저장·서버 영향 |
|---|---|---|
| 블록 선택·역할 영역 배치·순서 변경·직접 연결 + 전체 선택 설명 | 중간 | 기존 노드/연결/`relation`을 그대로 쓰면 DB migration·AI Worker 변경 없이 클라이언트 중심으로 가능 |
| 연결마다 자유 서술 추가·재조회 | 중간 이상 | 현재 edge 허용 필드는 `from/to/relationType`뿐이다. 새 설명 필드, 공용/서버 검증, 재조회·기록 표시와 구형 설치본 호환을 함께 변경해야 한다. JSONB가 있다고 무조건 저장 가능한 것은 아니다. 버전 설계에 따라 DB 제약 변경 여부를 정한다 |
| 자유 위치·확대/축소·분기/중첩을 가진 Scratch 수준 편집기 | 높음 | 좌표·계층·새 연결 규칙과 보존 방식을 설계해야 한다. 사이드패널 가독성·키보드 조작·재현·호환 검증도 크게 늘어난다 |

기존 고정 `relationType`을 자유 텍스트로 대체하면 구조 검증이 깨진다. 연결별 설명을 도입한다면 기존 논리 관계 코드와 학습자의 추가 서술을 별도 데이터로 두는 방안이 적합하다. 이를 필수로 만들지는 별도 설계 결정이다. 현행 공통 추가 설명 선택 정책을 이 검토만으로 바꾸지 않는다.

## 구현에서 실제로 어려운 부분

- 긴 원문 카드와 패널 스크롤 중 드래그를 함께 처리하고, 320px 폭에서도 놓을 자리를 구분하는 것.
- 블록을 옮겨도 노드 ID·출처·연결이 유지되게 하고, 역할 변경으로 유효하지 않게 된 연결을 사용자에게 명확히 알리는 것.
- 클릭/탭으로 고른 뒤 놓기, 위/아래 이동 버튼, 키보드 조작을 드래그와 같은 기능으로 제공하고 렌더링 후 초점도 보존하는 것. 키보드 지원만으로 드래그 대체 조작을 모두 충족하는 것은 아니다. [W3C 드래그 동작 안내](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- 원문 선택과 블록 이동이 충돌하지 않도록 이동 손잡이를 두고, 입력 장치별 포인터 취소·캡처를 처리하는 것. 표준 Pointer Events를 사용할 수 있다. [MDN Pointer events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)
- Retell 진입 시 블록·연결선·관계 입력·메뉴까지 함께 가리는 것. 별도 떠 있는 연결선/팝업 때문에 현재 가림 범위를 우회하지 않아야 한다.
- 후보를 모두 제거하거나 수동 작성으로 전환해도 실제 후보 노출 이력을 유지하는 것. 재배열·연결 UI 변경으로 AI 게이트를 다시 열지 않는다.

## 이번에 확인한 근거와 한계

- 합성 문장 3개로 기존 편집기의 그래프를 만들고 순서를 바꿔 기존 검증기에 넣었다. **재배열 허용·연결 ID 유지·바뀐 순서의 답안 문자열 직렬화**를 확인했다.
- 전체 연결 이유는 기존 `relation` 문자열 계약으로 수용된다. 반면 edge에 자유 서술 필드를 추가하면 현재 검증기가 거절함을 확인했다.
- 대화의 조작 예시는 원문 문장 선택, 역할 영역에 놓기, 위/아래 이동, 직접 연결, 선택 설명을 보여주는 독립된 구상안이다. 제품과 연결하거나 배포하지 않았다. 예시는 주장–근거 유형만 표현한다.
- 예시의 JS 구문·요소 참조·연결/이동 처리와 네트워크 요청 부재를 점검했다. 실제 브라우저 미리보기는 로컬 파일 URL 정책 때문에 열리지 않아 시각·드래그 동작 검증을 완료하지 않았다. 다른 브라우저나 URL 변환으로 우회하지 않았다.
- 제품 코드·서버·DB·배포·기능 스위치를 변경하지 않았다. 기존 미커밋 문서도 보존했다. 설계 결정이 확정되면 요청서 변경 이력·완료 기준·변경이력에 반영한 뒤 구현한다.

## 후속 제안: 각 변 중앙의 연결점

- 사용자 의견: 역할 영역에 문장을 놓는 과정은 좋지만 기존 연결 버튼은 직관적이지 않다. 블록의 위/오른쪽/아래/왼쪽 변 중앙에 추가 가능한 연결점을 두고 다른 블록의 연결점으로 선을 잇는 방식을 제안했다. 현재는 가능성 검토이며 제품 구현 승인으로 확대하지 않는다.
- **구현 가능, 예상 난도 중간.** 기존 2–8개 문장·최대 16개 연결 안에서 네 연결점과 선 그리기를 프런트엔드에 추가할 수 있다. 연결점은 문장 노드에 붙는 조작 요소다.
- 조작안: 각 변 중앙의 `+` → 드래그 중 임시 선 → 다른 블록 연결점 근처에서 강조/스냅 → 선 확정. 같은 두 블록의 다른 연결점을 고르면 접점 위치를 바꿀 수 있다. 점을 차례로 클릭하는 대체 동작과 키보드/Esc 취소도 제공한다.
- 실제 난도는 점 자체보다 블록 이동·재배열/크기 변경에 선이 따라가게 하는 것, 선 겹침·가림, 좁은 화면의 터치 영역, 스크롤과 연결 드래그 구별에 있다. 네 변당 고정점 하나로 시작하고 무제한 접점·자유 캔버스·자동 선 회피는 첫 범위에서 제외하는 안이 적합하다.
- 관계만 저장할 경우 접점은 로컬 UI 상태로 두고 기존 `from/to/relationType`을 보낼 수 있다. 어느 변을 썼는지까지 재조회에서 정확히 복원하려면 `fromSide/toSide` 같은 접점 정보를 저장 계약에 추가하고 서버/클라이언트 검증·구형 호환을 보완해야 한다. 기존 JSONB 컬럼만으로 새 필드를 바로 수용하지는 않는다.
- 합성 검사에서 상하좌우 접점의 **16가지 조합**을 기존 의미 연결로 변환해 수용됨을 확인했다. 접점 필드를 그대로 추가하면 현재 그래프 검증기가 거절하는 것도 확인했다. DB·제품 API는 호출하지 않았다.
- 대화 예시는 기존 문장 선택·역할 배치를 유지하면서 네 연결점을 누르거나 드래그하는 방식으로 수정했다. 이 주장–근거 예시는 사용자가 고른 두 역할의 논리 방향을 근거→주장으로 표시한다. 제품의 방향 선택/확인 표현은 설계 확정 때 별도로 정하며 AI가 내용을 보고 연결을 만드는 기능은 아니다.
- Pointer capture를 이용하면 드래그가 작은 접점을 벗어나도 추적할 수 있다. [MDN setPointerCapture](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture). 드래그 대체 클릭 동작은 [W3C 지침](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)을 따른다.
- 예시의 JS 구문과 저장 계약 변환을 확인했으며 실제 브라우저의 드래그·터치·선 겹침 QA는 아직이다. 이전 로컬 파일 미리보기 보안 제한을 우회하거나 브라우저 확인을 재시도하지 않았다. 제품 코드·운영 서버는 변경하지 않았다.

## 후속 요구: 연결선 취소·삭제

- 사용자 요청으로 대화 속 조작 예시에 연결선 삭제를 명확히 드러냈다. 선을 클릭하거나 연결 목록에서 선택하면 강조하고 `선택한 선 삭제` 버튼을 표시한다. 같은 선택 상태에서 Delete/Backspace로도 삭제할 수 있다.
- 삭제는 해당 연결만 제거하고 문장 블록·역할·배열·선택 설명을 유지한다. 연결을 지운 뒤 다시 연결할 수 있다. 선의 실제 클릭 영역은 보이는 선보다 넓게 두며, 키보드 사용자는 연결 목록의 버튼으로 같은 대상을 선택할 수 있다.
- 입력란에서 글을 수정할 때 Delete/Backspace가 연결 삭제로 작동하지 않게 분리했다. Esc는 선을 그리거나 연결점을 선택하는 도중 취소에 쓴다. 취소 때 작성 중인 설명을 지우지 않는다.
- 기존 편집기에 `disconnect(from,to)`가 있어 제품 구현에서도 해당 의미 연결을 제거하는 로직은 재사용 가능하다. 별도의 서버 기능은 이 삭제 동작 자체에 필요하지 않다. 저장 후 최초 그래프를 편집하는 기능으로 범위를 확대하지 않는다.
- 이번 반영은 대화 조작 예시·검토 문서에 한정한다. 실제 제품·DB·Worker·배포는 변경하지 않았다. 실제 Chrome의 선 선택·키보드·터치 검증은 남아 있다.
