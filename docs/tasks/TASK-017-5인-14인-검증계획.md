# TASK-017 이후 5인·14인 검증 구현안

2026-11-10 / 요청서 TASK-017 v8 / Codex dev.

상태: **사용자 후속 결정에 따라 TASK-020 5인 준비 개발 착수**. 잔여 Chrome 검증은 [5인 사람 QA](TASK-020-5인-QA.md)로 옮겼으며 통과 처리하지 않는다. 아래는 단계별 기본 준비안이고 Google 이메일 사전 등록·자동 승인 구현/실제 설정 대기는 TASK-020 요청·결과를 우선한다. 실제 14인 확대 승인은 아니다.

## 구현 1: 계정과 단계별 참여 자격

- 기존 Supabase Auth·pilot_members·본인 자료 RLS를 재사용한다. 설치 파일·명단 파일·클라이언트 스위치만으로 자격을 판단하지 않는다. 참가자별 계정을 쓰며 공용 계정·공유 비밀번호를 배포하지 않는다.
- 권장 모델은 서버 관리 `검증 회차`와 `회차별 참여자`다. 회차에는 단계·시작/종료·활성 상태·허용 빌드·한도를, 참여자에는 회차/사용자/활성 상태를 둔다. 실제 UID·연락처 명단은 공개 설정·Git에 넣지 않는다. 작은 파일럿이라도 서버가 현재 회차와 허용 대상을 확인하게 한다.
- 새 테이블을 쓸 경우 RLS·명시적 권한·Data API 노출 설정을 함께 검토한다. 회차 관리 정보는 기본 비공개로 두고 클라이언트의 추가/역할 변경을 허용하지 않는다. 클라이언트가 읽을 필요가 있는 최소 정보만 별도 계약으로 제공한다.
- AI/제출/기록 Worker는 검증된 사용자, 기존 활성 멤버십, 회차 참여 자격을 확인한다. DB 직접 접근 경로도 RLS로 통제해 Worker만의 회차 검사 우회가 없도록 한다. 시험 종료는 새 AI/제출 허용과 기존 본인 기록 조회를 구분해 결정한다. 삭제 요청 처리 경로를 함께 유지한다.
- AI Worker는 현재 단일 UID·시험 기한 제한을 회차 기준으로 일반화한다. `PILOT_SELFTEST_ONLY=false`만 설정해 모든 기존 활성 계정으로 넓히지 않는다. 회차 없음·만료·미등록·설정 오류는 모델 호출/예산 예약 전에 거절한다. 참여 철회는 사용자 편집 가능 프로필 값이나 오래된 JWT 역할만으로 판단하지 않는다.
- 최소 검증 행렬: 같은 회차 활성 A/B, 비활성 C, 다른 회차 D, 미등록 E. A가 B의 원본·수정본을 읽거나 쓸 수 없고, AI 피드백의 sessionId를 B 것으로 바꿔도 호출되지 않아야 한다. JWT가 유효한 상태의 자격 회수도 확인한다. 합성 검사와 실환경 검사를 구분한다.

## 구현 2: 팀원 검증과 참가자 답안 열람 권한 분리

- 5인 점검에서는 팀원도 학습자처럼 자기 자료만 조회한다. 기존 SQL 초안은 team/operator 역할에도 교차 조회를 부여하지 않으며 현재 Worker도 owner_id를 확인한다.
- 사용자·팀원이 참가자 응답을 읽는 목표는 별도 기능이다. 필요하면 **특정 검토자 → 특정 회차/참가자**의 읽기 전용 권한과 부여·회수 이력, 접근 기록, 최소 표시 필드를 설계한다. 참가자 자료 수정·삭제 권한과 분리하고 고지·동의에 반영한다.
- 화면에 팀원 버튼을 보여주는 것만으로 허용하지 않는다. Worker/API와 RLS에서 검증하고 권한 없는 팀원·회수된 검토자·다른 회차 접근을 검사한다. 클라이언트에 service role/서버 Secret을 넣지 않는다.
- 이 열람 기능을 필수로 포함할지는 14인 착수 전에 확정한다. 미구현 상태를 완료라고 보고하거나 이번 5인 점검 승인으로 대신하지 않는다.

## 구현 3: 초대와 실제 설치

- 대상 빌드의 폴더·ZIP·SHA-256·고정 확장 ID를 하나로 정하고, 같은 패키지·설치 안내로 검증한다. 사용자에게 빌드·공개 설정 편집·로컬 서버 실행을 요구하지 않는다. OS/Chrome 버전·설치 경로·실패 단계만 최소 기록한다.
- 압축해제 설치는 제한된 파일럿의 후보 방식이다. 관리형 Chrome의 개발자 모드/확장 정책, 설치 지원 가능 여부를 5인에서 먼저 확인한다. 웹스토어 공개나 참가자 배포는 별도 결정이다.
- 실제 이메일 초대 경로를 1개 테스트 주소로 확인한 뒤 순차 진행한다. 기본 SMTP로 일반 참가자에게 발송 가능하다고 가정하지 않는다. Supabase 공식 문서는 기본 SMTP가 프로젝트 팀 외 주소로 발송하지 않는다고 안내한다. 이때 프로젝트 팀은 파일럿의 '팀원 5명'과 다른 조직 권한 개념이다. 참가자를 프로젝트 관리자에 추가하는 우회는 하지 않는다. [공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)
- 초대를 쓰려면 사용자 승인 후 적절한 메일 제공자·발송 도메인·리디렉션/수신 흐름·현재 발송 제한을 확인한다. 비밀번호/링크/연락처를 공개 문서·로그로 전달하지 않는다. 현재 세션은 실제 계정 생성·초대 발송을 하지 않았다. [Auth 제한 안내](https://supabase.com/docs/guides/auth/rate-limits)

## 구현 4: AI 호출 한도·기한·동시 사용

- 현재 본인 시험은 추천+피드백 합산 사용자/전체 UTC 일일 각각 5회다. 지정 본인만 허용하므로 계정 추가나 ZIP 전달만으로 5인/14인 AI가 가능해지지 않는다. 기록된 기한(2026-11-10 23:55:55 KST)도 새 회차에 재사용하지 않는다.
- 추천 1회+피드백 1회를 한 흐름의 기본 요청으로 보면, 한 번씩 사용해도 팀원 5명은 10회, 참가자 14명은 28회의 예약이 필요하다. 운영자 점검·실패도 소모하므로 기존 전체 5회로는 부족하다. 이 계산은 한도 산정용이며 실제 모델 성공·비용을 보장하지 않는다.
- 예시 검토안: 사용자 일일 4회, 5인 회차 전체 일일 20회, 14인 회차 전체 일일 56회. 운영자 점검의 계정/회차·예비분 포함 여부, 시험 일수, 최대 재시도를 확정한 뒤 승인받는다. 실제 배포 값이나 확대 승인이 아니다.
- 현재 Durable Object의 원자적 예약을 유지하고 회차별 일일/전체 기간 상한·동시 처리 수를 추가하는 안을 검토한다. 날짜는 UTC 기준임을 안내한다. 새 회차·배포·기한 변경이 기존 사용량을 임의 초기화하지 않도록 테스트한다. 금액 상한이 필요하면 별도 토큰/금액 예산 장치·제공자 제한을 설계하며 횟수 제한을 금액 보장으로 표현하지 않는다.
- 자동 모델 재시도를 하지 않는다. 연속 클릭·응답 유실의 중복 호출은 회차+사용자+학습 시도+요청 종류 기준의 중복 방지 설계를 검토한다. 만료/한도/제공자 장애에서도 직접 읽기·작성·제출·수정 저장은 가능한 상태를 유지한다.
- 합성 모델 응답으로 5/14개 동시 요청·일일/회차 한계 직전·만료·회수·부분 실패를 검증한 뒤, 승인된 실환경 비호출 검사와 소수 실제 UI 확인 순으로 진행한다. 실제 모델을 부하 테스트에 사용하지 않는다.

## 구현 5: 검증 기록·확대/중단 기준

- 첫 5인 검증은 별도 대시보드 없이 승인된 비공개 체크리스트로 수행할 수 있다. 검증 코드, 대상 빌드, 설치 여부, 단계별 성공/오류 코드, 재시도·재로그인 조회 결과, 완료/중단/차단을 기록한다. 실제 답안·기사 전문·이메일·토큰을 오류 로그에 추가하지 않는다.
- 14인 운영 집계 자동화가 필요하면 사전에 수집 목적·필드·보관·동의를 정한다. 서버가 검증할 수 있는 저장 성공과 본인 보고인 읽기/Retell 수행을 구분하고, 저장 한 건을 훈련 전체 완료로 추정하지 않는다. 참가자별 명단과 실제 응답은 공개 저장소 밖에서 관리한다.
- 추천 수용안: 5명 전원의 핵심 경로 결과가 확보되고, 자료 유실·중복 저장·타인 열람·읽기 중 AI 노출·잘못된 탭 가림 같은 치명 결함이 없어야 확대한다. 미완료/중단을 제외해 100% 성공으로 만들지 않는다. 비치명 문제와 수용 여부는 사용자/PM이 기록한다.
- 중단 조건: 타인 자료 노출, 읽기 중 답/요약 노출, 저장 완료 오표시·자료 유실, 통제되지 않은 비용/호출, 동의하지 않은 외부 전송. 원인 수정·해당 회귀·소수 재확인 후 재개한다. 중단 설정은 AI/새 참여와 기존 기록 조회·삭제 요청을 구분한다.
- 기존 파일럿 종료 후 30일 이내 삭제 및 조기 삭제 요청 규칙을 유지한다. 담당자·실제 보관처·원본/수정본/백업의 삭제·복구 후 재삭제는 실사용 전에 확인한다. 과거 운영 점검 연기 결정을 새 참가자 수용 기준 충족으로 간주하지 않는다. 제공자 처리·전송 조건도 확인한다.

## 권장 구현 순서와 사용자 결정

1. 사용자 v9 결정에 따라 TASK-017 잔여 Chrome 기준을 5인 사람 QA로 옮기고 TASK-020의 Google/자동 승인 배포 후보를 준비한다. 실제 사람 QA 대상으로 빌드·범위를 고정한다. 이전 직접 검증 중단은 [후속 검증 기록](TASK-017-후속검증.md)을 따른다.
2. 회차/대상·기한·한도 관리, 실패 거절, 역할/소유권 검증, 비밀 없는 배포 후보 생성과 합성 통합 검증을 별도 요청서로 만든다.
3. 5인 설치·초대 전달·합성 전체 흐름과 사용성 관찰을 수행한다. 별도 승인 후 필요한 실환경 변경을 적용한다.
4. 팀원 답안 열람의 필요/범위, PDF 포함 여부, 고지/동의·지원·보관/삭제·AI 예산을 확정하고 14인 소수부터 진행한다.

실제 명단·일정·초대 발송·메일 제공자/비용·모델 호출·배포·DB 변경·참가자 자료 수집은 이번 준비안에서 실행하지 않았다.

기술 근거: 현재 server/ai/pilot-worker.mjs, server/submissions/worker.mjs·records.mjs, server/migrations/001-pilot-draft.sql 및 TASK-012/013/015/017. 실제 환경은 별도 재확인한다. 공식 [RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)와 [변경 이력](https://supabase.com/changelog)을 확인했다. 신규 테이블이 필요하면 Data API 노출·GRANT와 RLS를 별도로 검토한다.
